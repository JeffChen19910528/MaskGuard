# MaskGuard OCR Engine Benchmark

Objectively compares OCR engines' effect on the real, **unmodified**
MaskGuard pipeline (`Detection -> Risk -> Policy -> Redaction ->
Verification`). This is measurement tooling, not a replacement for
Tesseract and not part of the production package — `maskguard/` never
imports anything from `benchmarks/`.

## Architecture

```
benchmarks/ocr/
├── engines.py    # TesseractOcrEngine (= production LocalOcrEngine) and the
│                 # PaddleOcrEngine adapter — both implement maskguard's own
│                 # IOcrEngine, so no OCR-specific data type ever reaches
│                 # Detection/Risk/Policy/Verification.
├── dataset.py    # Synthetic image + ground-truth generator.
├── metrics.py    # CER, IoU, detection recall/precision/FN/FP — pure functions.
├── runner.py     # Runs one engine's tokens through the real detection ->
│                 # risk -> policy -> redaction -> verification stages and
│                 # scores the result against ground truth.
├── report.py     # Writes benchmarks/results/ocr_benchmark_<date>.{json,csv}.
└── run.py        # CLI: python -m benchmarks.ocr.run
```

`tests/ocr_benchmark/` holds the pytest-visible half: dataset/metrics unit
tests (no OCR needed), a fake-engine runner smoke test (no OCR needed), and
the real-Tesseract full-dataset run — gated behind the `benchmark` pytest
marker (`pytest -m benchmark`), excluded from the default `pytest` run the
same way `pytest -m e2e` is. The one exception is
`tests/test_ocr_segmentation_equivalence.py`, which lives at the top level
and runs under plain `pytest` — it's a cheap, deterministic security
regression test (see below), not something that needs gating behind real
OCR availability.

## Dataset

Synthetic only — no real personal data. Generated by
`benchmarks/ocr/dataset.py:generate_dataset()`, same fabrication policy as
`scripts/generate_test_images.py` (the credit card number is the universal
Luhn-valid *test* number; Taiwan ID/passport/bank account/API key/password
values only match the expected *format*).

**9 major sensitive types** (Taiwan ID, Passport, Bank Account, Credit Card,
Email, Taiwan Phone, API Key, Password, Address), each rendered under
**5 image conditions**:

| Condition    | How it's produced                                   |
|--------------|-------------------------------------------------------|
| `clean`      | Rendered directly, font size 30                       |
| `low_res`    | Downscaled 50% then upscaled back (BILINEAR)           |
| `blurred`    | `PIL.ImageFilter.GaussianBlur(radius=1.3)`             |
| `rotated`    | Rotated 6° with `expand=True`                          |
| `font_large` | Re-rendered at font size 42                            |

Plus **6 language/context-variety images** (clean only): English text,
Traditional Chinese text, mixed Chinese/English, a Chinese-labeled field
("姓名：王小明"), normal non-sensitive text (for measuring false positives),
and one **multiple-sensitive-values** image combining six different types in
one document — **51 images total**, a deliberately controlled set rather
than an exhaustive combinatorial matrix.

Each image gets a ground-truth entry in `ground_truth.json`:

```json
{
  "image": "TaiwanID_clean.png",
  "category": "TaiwanID",
  "condition": "clean",
  "text": "身分證：A123456789",
  "sensitive": [{"type": "TaiwanID", "bbox": [144, 24, 174, 27]}]
}
```

Ground truth is regenerated fresh in a temp directory by the pytest suite
and is never written to (or read from) the production audit log.

### Rotation ground-truth transform

`condition_rotated()` carries a bounding box through `Image.rotate(angle,
expand=True)` by applying, to each of the box's 4 corners relative to the
original image center `(cx, cy)`:

```
dx, dy = x - cx, y - cy
x' =  dx*cos(θ) + dy*sin(θ)  + new_center_x
y' = -dx*sin(θ) + dy*cos(θ)  + new_center_y
```

then taking the axis-aligned bounding rectangle of the 4 transformed
corners (MaskGuard's own boxes, like Tesseract's, are always axis-aligned).
This was verified empirically before use — see
`tests/ocr_benchmark/test_dataset_generation.py
::test_rotation_bbox_transform_matches_actual_pixel_position`, which rotates
a single marker pixel and confirms the formula predicts its real position
in the rotated bitmap.

## Metrics (priority order, per the brief)

| Priority | Metric | Meaning |
|---|---|---|
| **P0** | False Negative count | Sensitive value never detected at all — MaskGuard's worst failure mode. |
| **P0** | Verification False PASS count | `VerificationEngine` reports PASSED, but an *independent* re-check (fresh OCR of the whole final image, not reusing the engine's own crop/box) still finds the raw ground-truth value. |
| P1 | Sensitive Detection Recall | TP / (TP + FN), matched by type + IoU ≥ 0.3. |
| P1 | Bounding Box IoU | Mean IoU of matched detections; classified GOOD (≥0.9) / ACCEPTABLE (0.7–0.9) / NEEDS_REVIEW (<0.7) — **a benchmark reporting parameter only**, never wired into production policy. |
| P2 | Precision | TP / (TP + FP). |
| P2 | False Positive count | A detection with no corresponding ground-truth region (e.g. anything reported on the "normal non-sensitive text" image). |
| P2 | Character Error Rate (CER) | Levenshtein edit distance / reference length, on the raw OCR text vs. the line's full ground-truth text. |
| P3 | Processing time | OCR / Detection+Risk+Policy / Redaction+Verification, timed separately per image. |

### Why Verification False PASS needs an *independent* check

`VerificationEngine` can only check the detections it was handed. If
Detection misses a value entirely, there is nothing to redact and nothing
for Verification to re-check — it reports PASSED correctly *for what it was
asked*, while the raw value is still 100% visible in the output. The
benchmark's `_independent_false_pass_check` (in `runner.py`) closes that gap
by re-OCR'ing the **whole final image** and checking it against the
ground-truth value independently of whatever the pipeline itself decided to
verify. See the Final Report for what this run actually found.

## OCR segmentation-difference security test

Per the brief's explicit example — Engine A reading `4111111111111111`,
Engine B reading `4111 1111 1111 1111` — `tests/test_ocr_segmentation_equivalence.py`
confirms the real, unmodified `VerificationEngine` + `normalize_for_verification`
(the P0-1 fix from the prior phase) treats both readings of the identical
un-redacted value as the same CreditCard, in both tokenization directions,
using two fake `IOcrEngine`s so it needs no real second OCR engine installed
and runs under plain `pytest`.

## Adding a new OCR engine

Implement `maskguard.ocr.base.IOcrEngine.recognize(image, languages) ->
list[OcrToken]`, converting whatever the engine natively returns into plain
`OcrToken`/`BoundingBox` — see `benchmarks/ocr/engines.py:PaddleOcrEngine`
for the adapter pattern. Nothing else in the framework, or in MaskGuard
itself, needs to change; `runner.run_benchmark()` takes any `IOcrEngine`.

PaddleOCR's adapter is implemented but **not installed or exercised** in
this benchmark run — installing `paddleocr`+`paddlepaddle` was judged too
heavy/risky for this environment. `check_paddleocr_available()` in
`env_check.py` detects this and `run.py` skips it gracefully rather than
failing.

## Running it

```bash
pytest                    # unit tests — excludes both e2e and benchmark
pytest -m e2e             # real-OCR E2E pipeline tests
pytest -m benchmark       # this framework's own tests, incl. the full real-Tesseract run
python -m benchmarks.ocr.run    # generates benchmarks/results/ocr_benchmark_<date>.{json,csv}
```
